# 서버 변경 기록 (`src/vibecut`)

통합 브랜치(`feature/react-integration`)에서 서버 코드를 바꾼 내역. 서버 코드 수정은 성준규 허락을 받았고, 바꾸기 전에 내용을 사용자에게 보여 준 뒤 적용한다.

| 날짜 | 파일 | 변경 | 이유 | 영향 | 확인 |
| --- | --- | --- | --- | --- | --- |
| 11-10 | `ai/client.py` `Usage` | `tokens_by_model: {모델: [입력 토큰, 출력 토큰]}` 필드 추가, `to_dict()`에 같은 키 추가 | 모델마다 단가가 달라(받아쓰기·장면 분석·컷 판단) 합계 토큰만으로는 비용을 계산할 수 없음 | 기존 키(`requests`, `cache_hits`, `prompt_tokens`, `output_tokens`, `by_model`)는 그대로. 작업 `metrics.ai_usage`와 `bench` 결과에 키 하나가 늘어남. 골든 스냅샷 영향 없음 | `pytest -q` 155개 통과, `ruff` 통과 |
| 11-10 | `ai/client.py` `transcribe_audio` | 429 응답의 `error.details`(QuotaFailure의 quotaId·quotaMetric·quotaValue, RetryInfo의 retryDelay)를 읽어 로그에 본문 그대로 남기고, 오류 메시지 앞에 `[한도 …, retryDelay Ns]` 요약을 붙임 (`quota_info`, `quota_summary`) | 1시간 측정에서 받아쓰기 429가 났는데 `message`만 200자로 잘려 남아 어느 한도(무료 등급인지, 분당인지)인지 알 수 없었음 | 로그·오류 문구만 바뀜. 키 값은 본문에 없어 로그에 남지 않음 | `pytest -q` 162개 통과(새 테스트 7개), 골든 3개 그대로, `ruff` 통과 |
| 11-10 | `ai/client.py` `_attempts` | 한도 초과(429)를 받으면 retryDelay만큼(없으면 60초) 기다렸다 다시 보냄, 최대 3번 (`QUOTA_RETRIES`). 받아쓰기에만 켬(`quota_retries=3`). retryDelay가 300초를 넘거나 quotaId가 하루 한도(`PerDay`)면 기다리지 않고 바로 실패. 대기는 `on_quota_wait` 콜백이 있으면 그쪽에 맡김 | 분당 한도로 보이는 429에서 바로 포기해 받아쓰기 전체가 글자 없는 `energy`로 넘어감 | 받아쓰기만 해당. 글 판단(`generate_json`)은 예전처럼 429면 기다리지 않고 대체 모델로, 장면 분석은 예전처럼 바로 실패. `_failure` 문구의 "무료 키는 모델마다 하루 횟수 제한"(원인과 상관없이 붙던 고정 문구)을 "Gemini 사용 한도 초과 (429)"로 바꿈 | 위와 같음 |
| 11-10 | `services/analysis.py` | 분석 작업이 `client.on_quota_wait`를 달아, 한도 대기 중 1초마다 작업 `message`를 "받아쓰기 한도 대기 중 n초 (다시 시도 k/3)"로 갱신하고 취소를 확인 | S3 화면에서 대기 중임을 보이게 (멈춘 것처럼 보이지 않게), 대기 중에도 취소되게 | 진행률(%)은 그대로, 메시지만 바뀜 | 위와 같음 |
| 11-10 | `analysis/stt/transcribe.py`, `engines.py` | 받아쓰기 엔진 실패 경고를 "받아쓰기 실패 (gemini, 조각 3/12): Gemini 한도 초과(429) — 한도 대기 후 3번 다시 시도했지만 실패, 한도 …. 다음 방식으로 넘어갑니다."처럼 바꿈. 몇 번째 조각에서 실패했는지 붙임. 실패 중 취소면 `Canceled`로 올림. 예전 고정 문구 "무료 키는 하루 25회" 삭제 | 실패가 분석 결과 `warnings`에 분명히 남게 | **대체 방식으로 넘어가는 동작은 그대로**(whisper → energy). 바꿀지는 성준규와 정할 일. React S3는 "받아쓰기 실패"로 시작하는 경고가 있으면 경고 목록을 펼쳐 보여 줌 | 위와 같음 |
